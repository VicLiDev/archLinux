# bootctl：systemd-boot 的管理命令

- **归属**：`systemd` 包自带，是 systemd-boot 组件的命令行前端，与 GRUB 无关
- **用途**：安装/更新 systemd-boot、查看固件与启动项状态、切换默认启动条目
- **前提**：UEFI 启动。BIOS 机器上 bootctl 直接报 `Not booted with EFI`

## 1. 它属于谁：四个容易混的东西

| 名称         | 归属          | 是什么                             | 对应命令                        |
|--------------|---------------|------------------------------------|---------------------------------|
| systemd-boot | systemd 包    | 一个 `.efi` 引导器程序，由固件加载 | 无                              |
| `bootctl`    | systemd 包    | 管理上述引导器的命令行工具         | `bootctl ...`                   |
| `efibootmgr` | efibootmgr 包 | 直接读写 NVRAM 启动项的独立工具    | `efibootmgr -v`                 |
| GRUB         | grub 包       | 另一个引导器，有自己的工具链       | `grub-install`、`grub-mkconfig` |

确认归属：

```bash
pacman -Qo "$(command -v bootctl)"     # /usr/bin/bootctl is owned by systemd
```

三个容易误解的点：

- `bootctl` **不是** GRUB 的工具。用 GRUB 引导的机器上它照样能跑，只会告诉你
  systemd-boot 没装进 ESP。
- `bootctl` 安装时会**自己写 NVRAM**（创建 `Linux Boot Manager` 项），不需要
  `efibootmgr` 配合。反过来说，改启动顺序用 `efibootmgr`，别指望 bootctl。
- 两个工具的视角不同：`efibootmgr` 看固件层（NVRAM 里有哪些项），`bootctl`
  看引导器层（ESP 上有哪些条目，文件里写了什么）。

## 2. 子命令一览

| 子命令                            | 作用                                                    |
|-----------------------------------|---------------------------------------------------------|
| `bootctl status`                  | 总览：固件、Secure Boot、ESP 位置、引导器版本、所有条目 |
| `bootctl install`                 | 把 systemd-boot 装进 ESP 并登记 NVRAM                   |
| `bootctl update`                  | 升级后把新版本引导器拷进 ESP                            |
| `bootctl list`                    | 只列可启动条目（含自动发现的 Windows/macOS）            |
| `bootctl set-default <id>`        | 设默认条目，等价于改 `loader.conf` 的 `default`         |
| `bootctl set-oneshot <id>`        | 只下次启动用，之后恢复默认                              |
| `bootctl is-installed`            | 检查是否已装，脚本里用退出码判断                        |
| `bootctl random-seed`             | 生成随机种子，通常由 systemd 服务自动调用               |
| `bootctl reboot-to-firmware true` | 下次重启直接进固件设置（改启动顺序很方便）              |
| `bootctl kernel-inspect <uki>`    | 查看 UKI 里打包了哪些内容                               |

常用参数：

```bash
sudo bootctl --esp-path=/efi install   # ESP 挂在 /efi 而不是 /boot
sudo bootctl --no-variables install    # 不写 NVRAM（由别的引导器统一管理时）
```

## 3. `bootctl status` 逐段怎么读

```text
System:
      Firmware: UEFI 2.70 (American Megatrends 5.27)   ← 固件类型与厂商
 Firmware Arch: x64
   Secure Boot: disabled (setup)                       ← 安全启动状态
  TPM2 Support: yes

Current Boot Loader:
      Product: systemd-boot 257.4-1-arch               ← 当前跑的引导器
     Features: ✓ Boot counting ✓ Menu timeout ...

Available Boot Loaders on ESP:
          ESP: /boot (/dev/disk/by-partuuid/xxxx-xxxx) ← ESP 挂载点
         File: └─/EFI/systemd/systemd-bootx64.efi

Boot Loader Entries:
        title: Arch Linux                              ← entries/*.conf 里的条目
           id: arch.conf
       source: /boot/loader/entries/arch.conf
        linux: /vmlinuz-linux
      options: root=UUID=xxxx rw
```

重点看三处：

1. **`ESP`** 是否指向预期的分区。为空或报 `Couldn't find EFI system partition`，
   说明 ESP 没挂载，或挂在 `/efi` 却没加 `--esp-path`。
2. **`Current Boot Loader` 的 `Product`**。显示 GRUB 或空白，说明当前不是
   systemd-boot 在引导，后面的条目列表也就没有意义。
3. **`Boot Loader Entries`** 是否有你要的条目。没有的话检查
   `/boot/loader/entries/*.conf` 是否存在、`linux` 路径是否写对。

## 4. 三个使用场景

### 4.1 安装

```bash
bootctl install
```

它做三件事：把 `systemd-bootx64.efi` 拷到 `/EFI/systemd/`、在
`/EFI/BOOT/BOOTX64.EFI` 放一份兜底（ESP 被重建或 NVRAM 丢失时还能启动）、
写一条名为 `Linux Boot Manager` 的 NVRAM 项。装完 systemd-boot 不执行这条，
固件根本不知道它的存在。

### 4.2 升级

```bash
bootctl update
```

systemd 包升级不会自动更新 ESP 里那份副本。新版 systemd 默认启用
`systemd-boot-update.service`，开机时自动同步；没启用的话手动执行上面的命令，
或者：

```bash
systemctl enable --now systemd-boot-update.service
```

### 4.3 切换默认条目

```bash
bootctl list                      # 看各条目的 id
bootctl set-default arch.conf     # 写进 loader.conf 的 default
bootctl set-oneshot windows.conf  # 只下次生效
```

## 5. 配置在哪：两个目录

```text
/boot/loader/loader.conf            # 全局：默认项、超时、控制台模式
/boot/loader/entries/*.conf         # 每个系统/内核一个条目
```

`loader.conf` 常用项：

```ini
default       arch.conf
timeout       3
console-mode  max
editor        no          # 禁止在菜单里按 e 改内核参数
```

条目文件最简形式（`root=` 用 UUID，别用 `/dev/nvme0n1p2` 这种会漂移的名字）：

```ini
title   Arch Linux
linux   /vmlinuz-linux
initrd  /initramfs-linux.img
options root=UUID=xxxx rw
```

字段只有两组用法，二选一：

| 用法     | 字段                           | 用途                             |
|----------|--------------------------------|----------------------------------|
| 传统内核 | `linux` + `initrd` + `options` | 从可读分区加载 vmlinuz           |
| 链式加载 | `efi`                          | 把另一个 `.efi`（如 GRUB）交出去 |

`efi` 的路径相对 ESP 根，例如 `/EFI/opensuse/shim.efi`。它不读任何文件系统，
所以能引导装在 btrfs 上的发行版；实例见 [02.dual-boot.md](02.dual-boot.md)
第 5.1 节。

**不需要“生成配置”这一步**：systemd-boot 每次开机直接读这些文件，改完重启就生效。
这是它和 GRUB 最大的操作差异，也是它“升级不容易炸”的原因。

## 6. 另一种形态：UKI（内核打包成 .efi）

如果 `bootctl status` 里同时出现 `Current Entry: xxx.efi` 与
`Current Stub: systemd-stub` 两段，说明这台机器用 UKI（Unified Kernel Image）
启动：内核、initramfs、内核参数被打进一个 `.efi`，放在 `/EFI/Linux/` 下。

| 事项           | 传统 vmlinuz          | UKI                         |
|----------------|-----------------------|-----------------------------|
| 条目从哪来     | 手写 `entries/*.conf` | 自动扫描 `/EFI/Linux/*.efi` |
| 内核参数写在哪 | 条目的 `options`      | `/etc/kernel/cmdline`       |
| 改完怎么生效   | 改 `.conf` 后重启     | `sudo mkinitcpio -P` 重建   |

开关在 `/etc/mkinitcpio.d/linux.preset`，默认是注释掉的，启用后大致如下：

```ini
default_uki="/boot/EFI/Linux/arch-linux.efi"
fallback_uki="/boot/EFI/Linux/arch-linux-fallback.efi"
```

路径里的 `EFI/Linux` 必须落在 ESP 上，与 `bootctl install` 用的 `--esp-path`
保持一致。

常用命令：

```bash
bootctl list                    # 自动条目也会列出来
cat /etc/kernel/cmdline         # 当前打包进 UKI 的内核参数
sudo mkinitcpio -P              # 改完 cmdline 后重建全部镜像
```

两个容易踩的点：

- UKI 条目**没有** `entries/*.conf`，照着旧教程改 `options` 不会生效。
- 手动条目照样能加，用 `efi` 做链式加载即可，与自动条目共存。

## 7. 与 GRUB 的边界

| 想做的事     | systemd-boot                           | GRUB                                   |
|--------------|----------------------------------------|----------------------------------------|
| 安装引导器   | `bootctl install`                      | `grub-install`                         |
| 更新菜单     | 改 `entries/*.conf`，无需生成          | `grub-mkconfig -o /boot/grub/grub.cfg` |
| 改默认项     | `bootctl set-default` 或 `loader.conf` | 改 `GRUB_DEFAULT` 后重新生成           |
| 探测其他系统 | 只自动发现 Windows/macOS               | `os-prober`（需手动打开）              |
| 查看 NVRAM   | `bootctl status` 或 `efibootmgr -v`    | `efibootmgr -v`                        |

一句话：**systemd-boot 是"静态文件 + 开机现读"，GRUB 是"用命令生成一份
grub.cfg"**。想在一个菜单里列出多个 Linux 发行版，systemd-boot 做不到，得换
rEFInd 或在 Arch 侧改用 GRUB（见 [02.dual-boot.md](02.dual-boot.md)）。

## 8. 常见报错

| 报错                                 | 原因                                         |
|--------------------------------------|----------------------------------------------|
| `Not booted with EFI`                | 机器是 BIOS 启动，bootctl 完全不可用         |
| `Couldn't find EFI system partition` | ESP 未挂载，或挂在 `/efi` 需加 `--esp-path`  |
| `Not booting from a FAT filesystem`  | ESP 被格式化成了 ext4 等非 FAT 文件系统      |
| `Failed to create EFI variable`      | NVRAM 只读/已满，或固件处于受限的 Setup Mode |

## 9. 验收清单

- [ ] `bootctl status` 里 `ESP` 指向正确分区，`Product` 是 systemd-boot
- [ ] `bootctl list` 能看到 `arch.conf` 等条目，`linux` 路径存在
- [ ] `bootctl is-installed; echo $?` 返回 0
- [ ] ESP 的 `/EFI/BOOT/BOOTX64.EFI` 存在（兜底引导器）
- [ ] 执行过一次 `bootctl update`，或确认 `systemd-boot-update.service` 已启用
- [ ] 若为 UKI 启动，`/EFI/Linux/*.efi` 存在且 `mkinitcpio -P` 能重建
