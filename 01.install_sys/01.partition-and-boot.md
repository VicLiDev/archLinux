# 分区与引导：ESP、GRUB / systemd-boot 到底装在哪

- **阶段**：装系统时 `fdisk` / `sgdisk` 分区之前，以及 chroot 里装引导器时
- **要回答的三个问题**：
  1. BIOS/UEFI、MBR/GPT、ESP/EFI 是什么关系，引导器最终写在磁盘哪里
  2. 分区是不是只要一个 ESP 挂到 `/boot`，为什么，留多大
  3. systemd-boot 和 GRUB 怎么选
- **结论先行**：UEFI 单系统 → GPT + 一个 ESP 挂 `/boot`（1 GiB 起步，我留
  5 GiB）+ systemd-boot；BIOS 老机器或需要复杂引导 → GRUB。

## 1. 固件、分区表与引导文件的落点

### 1.1 启动链

先把两条启动链摆出来，后面所有结论都是从这里推的：

```text
UEFI：固件 → NVRAM 里的 Boot#### 项 → ESP:/EFI/GRUB/grubx64.efi
      → /boot/grub/grub.cfg → /boot/vmlinuz-linux + initramfs → 切换根到 /

BIOS：固件 → 磁盘 MBR（前 512 字节）里的 boot.img → core.img（分区间隙）
      → /boot/grub/grub.cfg → 内核 + initramfs
```

### 1.2 BIOS 与 UEFI 的区别

**BIOS（legacy）**：固件只会把磁盘前 512 字节（MBR 扇区）读进内存并执行。
它不认识文件系统，所以引导代码必须写成纯机器码塞在那个扇区里，再由它把后续
代码（GRUB 的 `core.img`）从磁盘固定位置读出来。

**UEFI**：固件自带 FAT 驱动，会按 NVRAM 里的启动项去 ESP 分区上找 `.efi`
可执行文件并直接运行。它不需要"扇区引导代码"这一层，所以 UEFI 机器上
**MBR 里不会写 GRUB**——GPT 只在开头放一个保护性 MBR，防止老工具误认。

检测当前是哪种模式（Live 环境里第一步就能确认）：

```bash
[ -d /sys/firmware/efi ] && echo UEFI || echo BIOS
```

### 1.3 MBR 与 GPT

| 分区表 | 容量上限 | 主分区数 | 额外要求                                    |
|--------|----------|----------|---------------------------------------------|
| MBR    | 2 TiB    | 4        | 引导代码塞 MBR 扇区                         |
| GPT    | 8 ZiB    | 128      | UEFI 需要 ESP；BIOS+GPT 需要 BIOS boot 分区 |

MBR 是 1980 年代的结构，主分区只能有 4 个；GPT 用 GUID 标识分区类型，
拷贝分区表时有备份（磁盘尾部一份），所以现在一律用 GPT，除非机器老到只支持
BIOS 而你又想沿用 MBR。

**BIOS + GPT 是个特殊组合**：MBR 之后那段空隙在 GPT 上不再被视为可靠空间，
GRUB 要求单独切一个 1 MiB、无文件系统的 **BIOS boot 分区**（类型码 `ef02`）
来放 `core.img`。用 `sgdisk` 分区时忘了它，`grub-install --target=i386-pc`
会直接报错（提示找不到 BIOS boot partition）。

### 1.4 ESP、EFI、/boot 三个词

这三个词经常被混着说，其实是三个东西：

- **ESP（EFI System Partition）**：一个**分区**，GUID
  `C12A7328-F81F-11D2-BA4B-00A0C93EC93B`，`sgdisk` 类型码 `ef00`，
  文件系统必须是 FAT32（规范要求，固件只认 FAT）。
- **EFI 目录**：ESP 里的 `/EFI/`，各厂商的引导程序各占一个子目录
  （`/EFI/GRUB/`、`/EFI/systemd/`、`/EFI/Microsoft/`）。
- **`/boot`、`/efi`**：**挂载点**（普通目录）。把 ESP 挂到哪个目录，
  哪个目录就代表 ESP。Arch Wiki 两种主流做法是"ESP 挂 `/boot`"和
  "ESP 挂 `/efi` + 单独 `/boot`"，本文只推荐前者。

### 1.5 引导器实际写在哪

| 固件 + 分区表 | 引导代码位置                             | 启动项登记在哪           |
|---------------|------------------------------------------|--------------------------|
| BIOS + MBR    | MBR 前 446 字节 + MBR 后的 1 MiB 间隙    | 不登记，固件直接读 MBR   |
| BIOS + GPT    | MBR + BIOS boot 分区（1 MiB）            | 不登记                   |
| UEFI + GPT    | ESP 上的 `/EFI/<id>/*.efi`，**不写 MBR** | 主板 NVRAM（`Boot####`） |

由此得到一个很实用的差异：

- **BIOS 双系统**：装 Windows 时它会重写 MBR，GRUB 直接消失，必须进 Live
  环境 `arch-chroot` 重跑 `grub-install` 才能救回来。
- **UEFI 双系统**：Windows 在自己的 `/EFI/Microsoft/`，Arch 在
  `/EFI/GRUB/`（或 `/EFI/systemd/`），互不覆盖；最坏情况只是 NVRAM 启动顺序
  被改，用 `efibootmgr -v` 看看、`efibootmgr -o` 调一下就好。

查看当前机器的 NVRAM 启动项：

```bash
efibootmgr -v
```

## 2. 分区：ESP 挂到 /boot 就够

### 2.1 最小可用布局

| 分区 | 大小     | 类型码 | 挂载点   | 说明                                    |
|------|----------|--------|----------|-----------------------------------------|
| ESP  | 1–5 GiB  | `ef00` | `/boot`  | FAT32，引导器 + 内核 + initramfs 都在这 |
| root | 剩余空间 | `8300` | `/`      | ext4 / btrfs / xfs 随意                 |
| swap | 可选     | `8200` | `[SWAP]` | 内存够大可用 zram 或 swapfile 代替      |

也就是：**只切 ESP 和 root 两个分区**，ESP 挂 `/boot`，不需要单独 `/boot`、
更不需要 `/efi` + `/boot` 两套。

swap 那行是可选的：要不要建、建多大、建完谁来挂，单独写在 `05.swap.md`。

### 2.2 为什么 ESP 挂 /boot 就够了

1. **内核默认就装在 `/boot`**。`pacman -S linux` 把 `vmlinuz-linux` 放到
   `/boot`，`mkinitcpio` 把 initramfs 也生成到 `/boot`。把 ESP 挂在这儿，
   内核天然就在引导器能读到的地方，不需要任何拷贝步骤。
2. **UEFI 固件只认 FAT**。固件 → 引导器 → 内核这条链上，第一跳只能从 FAT32
   的 ESP 读文件。systemd-boot 没有文件系统驱动，内核必须在 ESP 上；
   GRUB 虽然有 ext4/btrfs 驱动，但要多一层模块加载，容易在升级后出问题。
3. **`/boot` 里没有需要 POSIX 语义的东西**。只有内核、initramfs、微码、
   `grub.cfg` / `loader.conf` 这类文件，不需要权限位、符号链接、硬链接，
   所以 FAT32 的"缺点"在这里不构成问题。
4. **少一层分区就少一类故障**。如果 ESP 挂 `/efi`、`/boot` 单独放 ext4，
   就必须维护"内核更新后把内核和 initramfs 复制到 ESP"的 hook（或改用
   systemd-boot 的 XBOOTLDR 方案）。hook 一旦失效，表现就是开机停在
   bootloader 里找不到内核——排查成本远高于多给 ESP 几 GB。

### 2.3 留多大：1 GiB 起步，5 GiB 宽裕

老教程里的 100–300 MiB 是按"一个内核 + 几十 MB initramfs"估的，现在不够用：

- `linux-firmware` 解包后几百 MB，即便 initramfs 只带需要的固件，fallback
  版本（关掉 `autodetect`、带上全部模块）也能到 100–200 MB；
- 实际使用中常同时装 `linux`、`linux-lts`（救命内核）、`linux-zen`，
  每个内核 = `vmlinuz` + `initramfs-*.img` + `initramfs-*.img.fallback`；
- 升级内核时 pacman 要**同时**写入新旧两套文件，瞬间占用翻倍；
- Windows 预装的 ESP 通常只有 100 MiB，想在这块 ESP 上装 Arch 会直接
  "No space left on device"，扩容又牵扯移动分区，非常麻烦。

所以：

- **1 GiB**：单内核 + 偶尔留个 fallback，能长期跑的下限；
- **5 GiB**：我自己的选择，留足余量——多内核共存、滚挂后回滚、
  临时塞统一内核镜像（UKI）、以后想加 `linux-zen` 都不用挪分区。
  5 GiB 对 FAT32 来说远没到上限（2 TiB），也不会因为簇大小浪费多少空间。

### 2.4 这么做的代价

- **`/boot` 无法被 btrfs 快照覆盖**：FAT32 不支持快照，所以"系统滚挂了
  回滚快照"救不了内核和 initramfs。对应做法是保留 `linux-lts` 作为备用
  entry，并用 `mkinitcpio -P` 保证 fallback 镜像可用。
- **Secure Boot 要更大空间**：用 `sbctl` 做统一内核镜像时，每个 UKI 几十 MB
  起，5 GiB 就比较舒服，1 GiB 会紧张。
- **不要试图把 `/boot` 设成 btrfs 子卷**：ESP 必须是 FAT32，二者不兼容。

### 2.5 什么情况才需要单独 /boot

只有极少数场景：想加密根分区但让 `/boot` 保持明文（GRUB 能解 LUKS，但要处理
LUKS2 + argon2 的兼容问题，通常得 `cryptsetup --pbkdf pbkdf2`），或者用
systemd-boot 的 XBOOTLDR 方案把内核放到 ext4 的 `/boot`、ESP 只挂 `/efi`。
这两种都增加复杂度，单系统普通安装没有理由选。

### 2.6 挂载与 fstab

```bash
mkfs.fat -F32 /dev/nvme0n1p1      # ESP
mkfs.ext4 /dev/nvme0n1p2          # root
mount /dev/nvme0n1p2 /mnt
mount --mkdir /dev/nvme0n1p1 /mnt/boot
genfstab -U /mnt >> /mnt/etc/fstab
```

`genfstab -U` 写的是 UUID，别手写 `/dev/nvme0n1p1`——盘序变化或插了新硬盘
之后设备名会变，UUID 不会。

## 3. systemd-boot 与 GRUB 怎么选

### 3.1 对比

| 维度         | systemd-boot                         | GRUB                             |
|--------------|--------------------------------------|----------------------------------|
| 固件支持     | 仅 UEFI                              | BIOS + UEFI                      |
| 配置方式     | 一个内核一个 `loader/entries/*.conf` | `grub-mkconfig` 生成 `grub.cfg`  |
| 内核位置     | 必须在 ESP（或 XBOOTLDR）            | 任意它支持的文件系统             |
| 文件系统     | 只认 FAT32                           | ext4 / btrfs / xfs / LVM / LUKS  |
| 加密 /boot   | 不支持                               | 支持（LUKS2 + argon2 需 pbkdf2） |
| 快照回滚     | 无对应方案                           | `grub-btrfs` 可在菜单里列快照    |
| 双系统       | 自动发现 Windows                     | 依赖 `os-prober`                 |
| 代码量与速度 | 小、启动快                           | 大、菜单渲染慢                   |
| 出错后的修复 | 加一个 `.conf` 或 `bootctl install`  | `grub-install` + `grub-mkconfig` |

### 3.2 选 systemd-boot 的理由

- 纯 UEFI 机器，单系统或与 Windows 共存；
- 配置就是几个纯文本 `.conf`，改错了看得懂、修得快；
- 内核更新不需要重新生成配置：entry 里写的是固定文件名
  （`/vmlinuz-linux`、`/initramfs-linux.img`），`mkinitcpio` 覆盖同名文件后
  下次启动自动生效；
- 依赖 `systemd` 本身，不额外引入一整套引导框架。

代价：内核必须待在 ESP，所以 ESP 不能小（这就是上一节要留 5 GiB 的直接原因）；
加密 `/boot`、复杂菜单、主题这些基本别想。

### 3.3 选 GRUB 的理由

- 机器只支持 BIOS（没得选）；
- 多系统、需要自定义菜单项、从 LVM/RAID 或加密 `/boot` 启动；
- 用 btrfs + `grub-btrfs`，想在开机菜单里直接选快照回滚；
- 已经熟悉 `grub-mkconfig` 那套，出问题知道往哪看。

代价：`grub.cfg` 是生成物，内核/主题/`os-prober` 任何一环变动都可能让菜单
缺项；UEFI 下还要同时维护 ESP 里的 `.efi` 和 NVRAM 启动项，坏起来比
systemd-boot 难查。

### 3.4 我的选择

- **UEFI 新机器**：GPT + 5 GiB ESP 挂 `/boot` + systemd-boot。分区最简单，
  配置最少，升级最不容易炸。
- **BIOS 老机器**：GRUB + `--target=i386-pc`，GPT 时记得留 1 MiB BIOS boot
  分区；若图省事就用 MBR。
- **需要加密 `/boot` 或要快照回滚菜单**：GRUB。

## 4. 落地：用 archinstall 安装

上面 1～3 节的手工流程是"知道自己在干什么"的版本；如果只是想尽快装好一台机器，
Live 环境里自带的 `archinstall` 能把分区、格式化、挂载、`pacstrap`、chroot 配置、
引导器安装一次性做完，本文讲的概念在它里面全部体现为几个选项。

```bash
archinstall          # ISO 自带；若版本过旧可先 pacman -Sy archinstall
```

### 4.1 手工步骤在 archinstall 里的对应位置

| 本文的手工步骤                     | archinstall 中的位置  | 注意                                     |
|------------------------------------|-----------------------|------------------------------------------|
| 分区、ESP 挂 `/boot`               | Disk configuration    | 默认布局的 ESP 偏小，要 5 GiB 得手动指定 |
| `mkfs` / `mount` / `genfstab`      | 自动完成              | 无需干预                                 |
| `pacstrap` 选内核与固件            | Kernels / Profile     | 额外包写进 Additional packages           |
| chroot 内的时区、locale            | Timezone / Locale     | 自动写入目标系统                         |
| 建用户、设密码、sudo               | User account          | 记得把用户加进 `wheel`                   |
| `grub-install` / `bootctl install` | Bootloader            | UEFI 默认 systemd-boot，BIOS 默认 GRUB   |
| 网络持久化                         | Network configuration | 选 NetworkManager 可顺带解决首次启动断网 |

最后一行值得强调：首次启动后没网、没 DNS（[02.first_boot/01.network.md](../02.first_boot/01.network.md)）
这类问题，根源就是安装阶段只做了临时配置；在 archinstall 里选 NetworkManager，
这一步会被自动写进目标系统，等于把那篇排障记录提前规避掉了。

### 4.2 想保留 5 GiB ESP 时

默认的 best-effort 布局会自己决定 ESP 大小（通常几百 MiB 到 1 GiB，随版本变化），
装完再扩容非常麻烦。要按本文的 5 GiB 来，就在 Disk configuration 里选手动分区：
先建一个 `fat32`、挂到 `/boot`、大小写 `5GiB` 的分区，再建 root。手动模式只影响
分区这一步，后面的格式化、挂载、装包仍然由 archinstall 自动做。

### 4.3 什么时候仍然建议手工装

- 想用 btrfs 子卷 + 快照、LVM、LUKS 加密这类默认布局不覆盖的结构；
- 需要精确控制挂载参数（`compress=zstd`、`noatime`、`ssd`）或分区对齐；
- 双系统，需要保留并复用 Windows 的 ESP、避免动到它的分区；
- 装完发现起不来——这时得放弃 archinstall，回到 1～3 节手工分区、重装引导器。

换句话说：**archinstall 省的是敲命令的时间，不是理解分区的必要**。第一次装建议
按 1～3 节手工走一遍，之后重装再用 archinstall 提速，出问题时才知道它替你做了什么。
