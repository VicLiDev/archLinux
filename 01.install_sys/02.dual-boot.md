# 双系统：Arch 与 openSUSE Leap 共存

- **背景**：机器上装了 Arch + openSUSE Leap，开机菜单里只有 Arch
- **结论先行**：UEFI 下两个系统各有独立引导器和 NVRAM 启动项，菜单不显示不代表
  openSUSE 被删了；先诊断再动手，多数情况一条 `efibootmgr` 就能解决
- **前提**：Arch 用 systemd-boot（本文以 ESP 挂 `/boot` 为例，挂 `/efi` 时自行换路径）

## 1. 先分清：菜单不显示 ≠ 系统丢失

UEFI 机器的启动链是三层，两个系统在这三层里是**并列**关系，不是从属关系：

```text
固件 → NVRAM 启动项（每个系统一项）→ 各自的 /EFI/<id>/*.efi → 各自的内核
```

- **ESP 是共享的**，但每个发行版只往自己的子目录写文件：systemd-boot 自己在
  `/EFI/systemd/`，UKI 内核镜像在 `/EFI/Linux/`，openSUSE 在 `/EFI/opensuse/`，
  互不覆盖；
- **NVRAM 里每个系统各有一条启动项**，固件只负责按顺序挑一条；
- **systemd-boot 的菜单只列它自己知道的东西**：`/boot/loader/entries/*.conf`
  里的条目、`/EFI/Linux/*.efi` 自动生成的条目（UKI 场景），加上自动发现的
  Windows/macOS。它**不会**列出其他 Linux 发行版的引导器——这是"只显示 Arch"
  最正常的原因。

所以先别重装，按下一节确认到底是哪一层出了问题。

## 2. 诊断：五条命令定位

```bash
bootctl status                            # Arch 用的是什么引导器
sudo efibootmgr -v                        # NVRAM 里有哪些启动项、当前顺序
lsblk -f                                  # ESP 挂在哪个分区、挂到哪
sudo ls -R /boot/EFI | head -30           # ESP 上各发行版的 .efi 在哪
sudo bootctl list                         # systemd-boot 实际能启动哪些条目
```

`ls /boot/EFI` 一定要加 `sudo`：ESP 通常按 `fmask=0137,dmask=0027` 挂载，普通
用户无法进入，而错误信息常被 `2>/dev/null` 吞掉，看起来就像"目录不存在"。
判断时以 `sudo` 的结果为准。

对照输出判断：

| 检查结果                                | 含义                                | 去哪一节 |
|-----------------------------------------|-------------------------------------|----------|
| `efibootmgr` 里有 `openSUSE` 项         | 启动项完好，只是不在默认菜单/顺序里 | 第 3 节  |
| ESP 上有 `/EFI/opensuse/`，NVRAM 里没有 | 引导文件在，NVRAM 项丢了            | 第 4 节  |
| 两者都有，但想要一个统一菜单            | systemd-boot 不会列其他发行版       | 第 5 节  |
| ESP 上也没有 `/EFI/opensuse/`           | 装 Arch 时格式化了共享 ESP          | 第 6 节  |

## 3. 情况 A：NVRAM 有项，只是没排第一

```bash
sudo efibootmgr                 # 看 BootCurrent / BootOrder / 各项编号
sudo efibootmgr -o 0003,0001,0000   # 按需要重排，编号用上面看到的
```

日常切换不必改顺序，开机时按固件键进启动菜单即可（品牌不同，常见是 F12、
F11 或 Esc，开机第一屏一般有提示）。

## 4. 情况 B：ESP 上有引导文件，NVRAM 项丢了

```bash
sudo efibootmgr -c -d /dev/nvme0n1 -p 1 \
  -L "openSUSE Leap" -l '\EFI\opensuse\grubx64.efi'
```

参数含义：

| 参数 | 含义             | 怎么确认                                |
|------|------------------|-----------------------------------------|
| `-c` | 新建启动项       | —                                       |
| `-d` | 磁盘设备         | `lsblk` 看 ESP 在哪个盘                 |
| `-p` | 分区号           | ESP 的分区编号，注意是**数字**不是 `p1` |
| `-L` | 菜单里显示的名字 | 随便写，建议带上发行版                  |
| `-l` | EFI 文件路径     | 反斜杠、`EFI` 大写，写错会静默失败      |

开了 Secure Boot 的机器要用 shim 而不是 grub：

```bash
sudo efibootmgr -c -d /dev/nvme0n1 -p 1 \
  -L "openSUSE Leap" -l '\EFI\opensuse\shim.efi'
```

建完用 `efibootmgr -v` 确认，再重启验证。删掉多余项用 `efibootmgr -b 0003 -B`。

## 5. 情况 C：想要一个菜单同时列出两个系统

### 5.1 systemd-boot 加一条 chainload 条目（首选）

适用：Arch 用 systemd-boot，两个系统的 `.efi` 都在同一个 ESP 上。这是共用 ESP
最常见的形态，也是本章最省事的做法——不装新软件、不动分区、不换引导器。

原理：systemd-boot 没有 btrfs 驱动，所以想直接写 openSUSE 的 `linux`/`initrd`
是走不通的；但 `efi` 指令只是把 FAT 上的一个 `.efi` 交出去，之后由 openSUSE
自己的 GRUB 去读它的 btrfs 根。**链式加载不需要文件系统驱动。**

| 写法               | 能跨 btrfs 吗 | 说明                             |
|--------------------|---------------|----------------------------------|
| `linux` + `initrd` | 不能          | systemd-boot 只认 FAT、ext4 等   |
| `efi`              | 能            | 只负责把 `.efi` 交出去，后面归它 |

第一步，确认引导文件在。openSUSE 的引导器在 ESP 的 `/EFI/opensuse/` 下：

```bash
sudo ls /boot/EFI/opensuse/
```

正常会看到 `shim.efi`、`grubx64.efi`、`grub.cfg` 之类。

第二步，写一个条目：

```bash
sudo tee /boot/loader/entries/opensuse.conf <<'EOF'
title   openSUSE Leap
efi     /EFI/opensuse/shim.efi
EOF
```

第三步，验证后重启：

```bash
sudo bootctl list        # 出现 "openSUSE Leap" 且没有 error
sudo reboot
```

几个要点：

- `efi` 的路径**相对 ESP 根**，写 `/EFI/opensuse/shim.efi`，不是
  `/boot/EFI/opensuse/shim.efi`。
- 开了 Secure Boot 用 `shim.efi`；关着的话直接写 `grubx64.efi` 少一层。
- 这条 `.conf` 里不要出现 `linux`、`initrd`、`options`，那是另一种用法。
- 手动条目与 `/EFI/Linux/*.efi` 自动生成的 UKI 条目共存，互不影响。
- 想固定默认项，改 `/boot/loader/loader.conf` 的 `default`，或用
  `sudo bootctl set-default opensuse.conf`。

### 5.2 rEFInd：扫描型，最省事

```bash
sudo pacman -S refind
sudo refind-install
```

rEFInd 会扫描**所有** ESP 上的 `.efi` 和内核，Arch、openSUSE、Windows 一次全列
出来，不需要为每个系统写配置。它和 systemd-boot 可以共存——rEFInd 甚至能把
systemd-boot 当作一个条目链式启动，所以不用先删掉现有引导器。

代价是多一层引导，开机多几百毫秒；界面和主题需要自己调。

### 5.3 Arch 侧换 GRUB + os-prober

```bash
sudo pacman -S grub os-prober efibootmgr
```

os-prober 默认被禁用，必须在 `/etc/default/grub` 里显式打开：

```ini
GRUB_DISABLE_OS_PROBER=false
```

```bash
sudo grub-install --target=x86_64-efi --efi-directory=/boot --bootloader-id=Arch
sudo grub-mkconfig -o /boot/grub/grub.cfg
grep -A2 "openSUSE" /boot/grub/grub.cfg     # 有输出才算探测成功
```

**openSUSE 特有的坑**：Leap 默认用 btrfs 子卷 + snapper，根子卷通常是
`@/.snapshots/1/snapshot`。os-prober 可能探测不到，或者探测到了但条目里缺
`rootflags=subvol=`，启动直接掉进 emergency shell。

遇到这种情况别反复调 os-prober，直接在 `/etc/grub.d/40_custom` 里手写条目更快：
先用 openSUSE 启动后 `findmnt /` 记下真实的子卷和 UUID，再照着写
`linux` / `initrd` 两行，最后重跑 `grub-mkconfig`。

### 5.4 什么都不装，靠固件菜单切换

适合"Arch 常用、openSUSE 偶尔进"的场景：开机按 F12 选 openSUSE，平时默认进
Arch。零维护成本，但每次都要按键。

## 6. 情况 D：ESP 上的 openSUSE 引导器已经没了

如果 `ls /boot/EFI` 里根本没有 `opensuse` 目录，说明装 Arch 时把共享 ESP 重新
格式化过。openSUSE 的根分区通常完好，只是引导文件丢了，用安装 U 盘修复：

1. 从 openSUSE Leap 安装介质启动，选 **Rescue System**（不是 Install）
2. 挂载原系统并 chroot：

```bash
mount /dev/nvme0n1p3 /mnt                     # openSUSE 根分区，用 lsblk 确认
mount /dev/nvme0n1p1 /mnt/boot/efi            # 共享 ESP
for i in dev proc sys; do mount --bind /$i /mnt/$i; done
chroot /mnt
```

3. 在 chroot 内重装引导器：

```bash
grub2-install --target=x86_64-efi --efi-directory=/boot/efi --bootloader-id=opensuse
grub2-mkconfig -o /boot/grub2/grub.cfg
```

注意 openSUSE 的 ESP 挂在 `/boot/efi`，而按本文档装的 Arch 把 ESP 挂在 `/boot`。
**同一个 ESP、两个挂载点**是正常的，不要以为是两个分区。

## 7. 共用 ESP 时的注意事项

- **装 Arch 时不要格式化共享 ESP**（`mkfs.fat` 那一步），只挂载即可；一旦格式化，
  另一个系统的引导文件全部消失，就得走第 6 节。
- **ESP 容量要够**：openSUSE 的引导文件加上 Arch 的内核、initramfs，1 GiB 往往
  吃紧，这也印证了安装阶段建议的 5 GiB。
- **UKI 更占地方**：Arch 用 UKI 时，每个镜像（含 fallback）在 `/EFI/Linux/`
  下各占几十 MB，且和 openSUSE 的 `/EFI/opensuse/` 同处一个 FAT 分区。
- **openSUSE 会抢回第一启动项**：它每次更新内核或跑 `grub2-install`，都会把自己
  的 NVRAM 项设为第一。开机突然进 openSUSE 不是 Arch 坏了，`efibootmgr -o` 调回
  即可。
- **Secure Boot**：开了的话 Arch 侧需要签名或用 shim，openSUSE 自带 shim 可直接
  启动；两个系统的 Secure Boot 状态互不影响，因为各自签各自的。
- **备份 ESP**：`sudo tar czf esp-backup.tar.gz -C /boot/EFI .`，改坏了能马上还原。

- [ ] 两条项的路径都指向真实存在的 `.efi` 文件
- [ ] 重启后能进 openSUSE，且 openSUSE 的 GRUB 菜单里也能看到 Arch
- [ ] 再重启回 Arch，系统时间、挂载都正常
- [ ] 若用 chainload 条目，`sudo bootctl list` 里能看到它且路径指向真实文件
